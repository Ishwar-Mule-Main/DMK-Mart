## A.2 Project Background

DMK Mart is a **trading and distribution firm** that **purchases finished products from manufacturers or distributors** and **sells them to B2B buyers and B2C walk-in customers** in bulk, packets, pieces, sets, or single units. The product range is focused on **plastic-manufactured goods** — chairs, buckets, kitchenware, household items, and industrial goods — currently 500+ SKUs and growing.

The client currently operates with fragmented tools (spreadsheets, manual ledgers, paper orders) and requires a **single dedicated software platform** to manage:

- All **orders** (purchase + sales)
- All **finance** (double-entry bookkeeping, journals, ledgers, P&L, balance sheet)
- All **inventory** (dual-stock: sellable vs. damaged/broken)
- All **firm/company data** (multiple firms, each fully isolated)
- **AI-assisted operations** (copilot, low-stock alerts, decision support)

**Critical Architecture Constraint (NEW):** This software is for **a single owner only**. There is **NO multi-user system, NO roles, NO permissions matrix**. The **firm/company is the account**. The owner logs in once and switches between firms.

## B.5 Inventory Management (Dual-Stock)

### B.5.1 The Dual-Stock Model

Every product tracks **two separate stock pools**:

| Pool | Meaning | Can Be Sold? |
|---|---|---|
| **Sellable Stock** | Good-condition, approved stock available for sale | ✅ Yes |
| **Damaged / Broken Stock** | Cracked, broken, transit-damaged, defective items in quarantine | ❌ No |

**Hard Invariant:** Billing can only draw from **Sellable Stock**. The system must never allow selling from Damaged Stock.

### B.5.2 Stock Movement Rules (Complete Matrix)

| Event | Sellable Stock | Damaged Stock | Voucher |
|---|---|---|---|
| Purchase received (good qty) | ↑ increases | — | Purchase |
| Purchase received (damaged qty) | — | ↑ increases | Purchase (quarantine) |
| Purchase Return (damaged returned to vendor) | — | ↓ decreases | Debit Note |
| Sales Order / Invoice | ↓ decreases | — | Sales + COGS |
| Sales Return (customer returns broken items) | — | ↑ increases | Credit Note |
| Internal damage (warehouse breakage) | ↓ decreases | ↑ increases | Stock Adjustment |
| Write-off / disposal of damaged | — | ↓ decreases | Journal |

### B.5.3 Low Stock Alert System

- Every product has a **Low Stock Threshold**.
- When sellable stock ≤ threshold, the system raises an alert.
- Alerts appear as:
  - **Dashboard notification/badge**
  - **Popup / notification center alert**
  - **AI copilot proactive alert**
- Alerts show: product name, current stock, threshold, and suggested reorder quantity.
- Optional one-click **"Create Purchase Order"** from the alert.

### B.5.4 Stock Valuation

- **Valuation method:** Weighted Average Cost (default).
- Every stock movement is logged in an **Inventory Movement Ledger** (date, product, qty, direction, source document) for full auditability.

## B.6 Purchase Workflow

### B.6.1 Vendor Accounts (Manufacturer vs Distributor)

When creating a **vendor account**, the owner selects the vendor type:

| Vendor Type | Behavior |
|---|---|
| **Manufacturer** | Shows **only that manufacturer's own brand products** when selecting items for a PO. Brand-scoped selection. |
| **Distributor** | Shows **all available products** (multi-brand), searchable by keyword. |

**Vendor profile fields:** Vendor name, type (Manufacturer/Distributor), GSTIN, state code, address, phone, payment terms (e.g., Net 30), opening balance, outstanding payable.

### B.6.2 Purchase Order (PO) Lifecycle

```
Create PO (select vendor, add products, qty, unit cost)
   │
   ▼
PO Status: PENDING  ← can be edited or cancelled here
   │
   ▼
Goods arrive at warehouse → Receive (GRN)
   │
   ├─ Enter received quantity
   ├─ Split into: Accepted (good) vs Damaged
   │
   ▼
PO Status: CONFIRMED / RECEIVED
   │
   ▼
Auto-post to Accounting & Finance (with date):
   • Inventory ↑ (accepted qty)
   • Damaged stock ↑ (damaged qty)
   • Vendor Payable ↑
   • Purchase Journal + ITC (Input Tax Credit) recorded
```

**Key Rules:**
- While **PENDING**, the PO can be **re-edited** (add/remove products, change qty) or **cancelled**.
- Once **confirmed/received**, editing is locked; changes go through Purchase Return.
- Every confirmation updates **inventory and finance with the transaction date**.

### B.6.3 Purchase Return (Debit Note)

When products are damaged or rejected:

```
Select PO / products → Create Purchase Return
   │
   ├─ Enter damaged quantity being returned
   ├─ Reason (transit damage / defective / wrong item)
   │
   ▼
Effects:
   • Damaged Stock ↓ decreases
   • Vendor Payable ↓ decreases
   • Debit Note generated
   • ITC reversed
   • Journal posted (dated)
```

### B.6.4 Vendor Payments

- Record payments to vendors (Bank/NEFT/UPI/Cheque/Cash).
- Each payment: reduces Vendor Payable, posts Payment journal, updates vendor ledger running balance.
- Supports **partial payments** and tracks outstanding.

### B.7.3 Sales Order / Invoice Lifecycle

```
Create Sale (select customer, add products, qty, pricing tier)
   │
   ▼
System checks:
   • Sellable stock available?
   • Credit limit OK? (for B2B credit sales only)
   │
   ▼
GST calculated (CGST+SGST intra-state / IGST inter-state)
   │
   ▼
Invoice generated (A4 statutory format, downloadable/printable)
   │
   ▼
Auto-post to Accounting & Finance (dated):
```

### B.7.4 Sales Return (Credit Note)

When a customer returns products:

```
Select invoice / products → Create Sales Return
   │
   ├─ Enter returned quantity
   ├─ Mark condition (broken/damaged)
   │
   ▼
Effects:
   • Returned qty → added to DAMAGED STOCK (not sellable)
   • Customer Receivable ↓ OR refund
   • Credit Note generated
   • Output GST reversed
   • Sales Returns contra-revenue posted
```

**Critical Rule:** Sales returns of broken/damaged items go to **Damaged Stock**, never back to Sellable Stock.

## B.8 Pricing Engine

### B.8.1 Five-Tier Pricing

Every product has five price tiers (defined in B.4.1). The customer's assigned tier determines the base price used in B2B billing.

### B.8.2 Quantity-Based Bulk / Packaging Pricing (Sales Only)

This applies **only to the Sales / Customer / Buyers section**. Prices change automatically based on quantity and packaging format:

**Packaging Format Discount Table:**

| Packaging Format | Unit Multiplier | Discount |
|---|---|---|
| PIECE (single) | 1 unit | 0% |
| PACKET | 5 units | 5% |
| SET | 10 units | 8% |
| BOX | 12 units | 12% |
| CRATE | 24 units | 15% |
| MASTER LOT | 50+ units | 20% |

**Effective Price Formula:**
```
Effective Unit Price = Tier Price × (1 − Packaging Discount) × (1 − Manual Discount)
Line Taxable Amount  = Round(Effective Unit Price × Quantity, 2)
```

**Example:**
- Product base (Wholesale tier): ₹235.00
- Customer orders 24 units (2 boxes) → BOX_12 format → 12% discount
- Effective price = 235 × (1 − 0.12) = ₹206.80
- Line amount = 206.80 × 24 = ₹4,963.20
- Customer saves ₹676.80 by buying in bulk

## B.9 Financial Accounting & Bookkeeping

### B.9.1 The Double-Entry Foundation

Every monetary event posts a **balanced journal entry** where:

```
Σ Debits = Σ Credits   (always, for every transaction)
```

This is the core invariant. The system never allows an unbalanced entry.

### B.9.2 Chart of Accounts (Per Firm)

Each firm has its own chart of accounts, grouped by class:

| Class | Examples |
|---|---|
| **Assets** | Cash in Hand, Bank Accounts, Accounts Receivable (Sundry Debtors), Inventory Asset, GST Input Tax Credit (ITC) |
| **Liabilities** | Accounts Payable (Sundry Creditors), GST Output Payable (CGST/SGST/IGST), TDS Payable |
| **Equity** | Owner's Capital, Retained Earnings |
| **Revenue** | Domestic Sales Revenue, Sales Returns (contra) |
| **Expenses** | Cost of Goods Sold (COGS), Purchases, Freight, Operating Expenses |

### B.9.3 Journal Voucher Types

| Voucher | Trigger |
|---|---|
| **Sales** | Sales invoice posted |
| **Purchase** | Purchase / GRN confirmed |
| **Receipt** | Money received from customer |
| **Payment** | Money paid to vendor |
| **Journal** | Manual adjustments, opening balances |
| **Contra** | Cash ↔ Bank transfers |
| **Credit Note** | Sales return |
| **Debit Note** | Purchase return |

### B.9.4 Party Ledgers with Opening & Closing Balances

Every **customer and vendor account** maintains:

- **Opening Balance** (as of FY start)
- **Running transaction history** (invoices, payments, notes)
- **Closing Balance** (live, real-time)
- **Balance type** — `Dr` (they owe us / receivable) or `Cr` (we owe them / payable)

**This applies to ALL accounts** — every party shows opening and closing balances, updated by every order, return, and payment.

### B.9.5 Financial Statements (Real-Time)

| Statement | Description |
|---|---|
| **Trial Balance** | All account balances; Σ Debits must equal Σ Credits |
| **Profit & Loss** | Revenue − COGS = Gross Profit; − Expenses = Net Profit |
| **Balance Sheet** | Assets = Liabilities + Equity |
| **Day Book** | Chronological list of all vouchers for a date |

### B.9.6 Financial Year Management

- Each firm operates on a financial year (e.g., 2025–26, April–March).
- Year switching; opening balances carried forward.
- Period closing to lock completed periods.

### B.9.7 Accounts Receivable / Payable Aging

- **AR Aging** — buckets 0–30, 31–60, 61–90, 90+ days for receivables.
- **AP Aging** — same buckets for payables.
- Supports credit control and cash-flow planning.

## B.10 GST & Statutory Compliance

### B.10.1 GST Calculation Logic

**Place of Supply determines the tax split:**

```
If Seller State Code = Buyer State Code  →  INTRA-STATE
    CGST = Taxable × (GST Rate / 2)
    SGST = Taxable × (GST Rate / 2)
    IGST = 0

If Seller State Code ≠ Buyer State Code  →  INTER-STATE
    IGST = Taxable × GST Rate
    CGST = 0, SGST = 0
```

State codes are derived from the GSTIN prefix.

### B.10.2 Invoice Requirements

Every tax invoice includes:
- Firm GSTIN, name, address
- Customer GSTIN (for B2B), name, address
- Invoice number (sequential, firm-specific) and date
- HSN code per item
- Taxable value, CGST/SGST/IGST breakdown
- Total, round-off, and **Amount in Words** (Indian numbering: Lakhs/Crores)

### B.10.3 Round-Off (Rule 545)

Invoice totals are rounded to the nearest rupee; the difference is posted to a **Round-Off account**.

### B.10.4 Input Tax Credit (ITC)

- Purchases record ITC as an asset.
- Purchase returns reverse ITC.
- Support for GSTR-2B reconciliation (matching vendor filings).

## C.4 Business Logic Engines

### C.4.1 GST Calculation Engine

```typescript
function calculateGST(taxable: number, gstRate: number,
                      sellerState: string, buyerState: string) {
  if (sellerState === buyerState) {
    // Intra-state
    const cgst = round2(taxable * (gstRate / 200));
    const sgst = round2(taxable * (gstRate / 200));
    return { cgst, sgst, igst: 0 };
  } else {
    // Inter-state
    const igst = round2(taxable * (gstRate / 100));
    return { cgst: 0, sgst: 0, igst };
  }
}
```

### C.4.2 Pricing Engine

```typescript
function calculateBulkPricing(tierPrice: number, quantity: number,
                              manualDiscountPct: number = 0) {
  let format = 'PIECE', discountPct = 0;
  if (quantity >= 50)      { format = 'MASTER_LOT_50'; discountPct = 20; }
  else if (quantity >= 24) { format = 'CRATE_24';      discountPct = 15; }
  else if (quantity >= 12) { format = 'BOX_12';        discountPct = 12; }
  else if (quantity >= 10) { format = 'SET_10';        discountPct = 8; }
  else if (quantity >= 5)  { format = 'PACKET_5';      discountPct = 5; }

  const unitPrice = round2(tierPrice * (1 - discountPct/100)
                                       * (1 - manualDiscountPct/100));
  const taxable   = round2(unitPrice * quantity);
  const savings   = round2((tierPrice * quantity) - taxable);
  return { format, unitPrice, discountPct, taxable, savings };
}
```

### C.4.3 Double-Entry Journal Posting

Every transaction posts a balanced journal. Example — Sales Invoice:

```
Dr. Customer A/R (or Cash/Bank)    = grand_total
Cr. Sales Revenue                  = taxable
Cr. CGST Output Payable            = cgst
Cr. SGST Output Payable            = sgst
Cr. IGST Output Payable            = igst
Dr/Cr. Round-Off                   = round_off delta
```
Plus COGS companion:
```
Dr. Cost of Goods Sold             = cost
Cr. Inventory Asset                = cost
```

### C.4.4 Stock Update Logic

```typescript
// On Sales Invoice
product.stock_quantity -= quantity;   // sellable only

// On Sales Return
product.damaged_stock += quantity;    // NOT sellable

// On Purchase Confirm
product.stock_quantity += acceptedQty;
product.damaged_stock  += damagedQty;

// On Purchase Return
product.damaged_stock  -= quantity;
```

# 🅳 PART D — FRONTEND DESIGN SYSTEM (MIDNIGHT LEDGER)

## D.1 Design Philosophy

The DMK Mart ERP uses a **Dark-First, High-Contrast, Navy-Based** design language engineered for long working sessions, financial clarity, and professional trust. The palette is a deep midnight navy canvas with electric action accents, ensuring money and actions stand out against a calm background.

**Core Principles:**
1. **Money in Motion** — Orange/gold accents reserved for financial figures and actions.
2. **Calm Canvas** — Deep navy background reduces eye strain during long bookkeeping sessions.
3. **Clarity Over Decoration** — Clean tables, readable numerics, no visual noise.
4. **Consistent Density** — Standardized spacing, control heights, and type scale across all modules.
5. **Responsive Everywhere** — Identical functionality on desktop, laptop, tablet, and mobile.

# 🅴 PART E — AREA-WISE WORKFLOW MANUAL

## E.1 Firm Setup Workflow

```
1. Owner logs in (single credential)
2. On first launch → "Create Your First Firm" wizard
3. Enter firm details (name, code, GSTIN, state, address)
4. Enter bank & contact
5. Select financial year + invoice prefix
6. Upload logo (optional)
7. Enter opening balances (cash, bank)
8. System seeds Chart of Accounts for the firm
9. Firm ready → Owner lands on Dashboard
10. To add another firm → Settings → Firms → [+ Create New Firm]
11. To switch → Header Firm Switcher → select firm
```

**Outcome:** Each firm is a fully isolated workspace with its own products, parties, orders, and books.

## E.2 Product Management Workflow

### E.2.1 Add Single Product

```
Inventory → Products → [+ Add Product]
  → Fill SKU, name, category, unit, HSN, GST rate
  → Enter purchase cost
  → Enter 5-tier prices (system validates Tier1 ≤ ... ≤ Tier5)
  → Enter opening stock (sellable) + damaged stock
  → Set low-stock threshold
  → Save
```

### E.2.2 Bulk Upload Products

```
Inventory → Products → [Bulk Upload]
  → Download CSV/Excel template
  → Fill offline
  → Upload file
  → System validates each row
  → Preview: valid rows + invalid rows (with reasons)
  → Confirm → import valid rows
  → Summary: X created, Y updated, Z failed
```

```
  → Update fields → Save

```

## E.3 Purchase Workflow

### E.3.1 Create Vendor

```
Purchase → Vendors → [+ Add Vendor]
  → Select type: Manufacturer | Distributor
  → If Manufacturer → enter brand name (scopes product selection)
  → Enter name, GSTIN, state, phone, payment terms
  → Enter opening balance
  → Save
```

### E.3.2 Create Purchase Order

```
Purchase → Purchase Orders → [+ New PO]
  → Select vendor
    • If Manufacturer → product search shows only that brand
    • If Distributor → product search shows all products
  → Add products (typeahead search), qty, unit cost
  → System computes taxable + GST (by vendor state)
  → Save as PENDING
```

### E.3.3 Edit / Cancel Pending PO

```
PO Register → select PENDING PO
  → [Re-Edit] → add/remove products, change qty → Save
  → [Cancel] → enter reason → PO cancelled
```

### E.3.4 Confirm Receipt (GRN)

```
PO Register → select PENDING PO → [Confirm Inward]
  → Enter received quantity per line
  → Split: Accepted (good) vs Damaged
  → Confirm
  → System:
     • stock_quantity += accepted
     • damaged_stock  += damaged
     • vendor closing_balance += grand_total
     • vendor ledger row added (PURCHASE, Cr)
     • Purchase journal posted:
        Dr Inventory (subtotal)
        Dr ITC (tax)
        Cr Vendor Payable (grand total)
  → PO status → CONFIRMED
```

### E.3.5 Purchase Return (Debit Note)

```
Purchase → Purchase Returns → [+ New Return]
  → Select vendor + reference PO
  → Add damaged products + qty + reason
  → Confirm
  → System:
     • damaged_stock -= qty
     • vendor closing_balance -= return_total
     • vendor ledger row (DEBIT_NOTE, Dr)
     • Debit Note journal:
        Dr Vendor Payable
        Cr Purchases (taxable)
        Cr ITC reversal (tax)
```

### E.3.6 Vendor Payment

```
Purchase → Vendor Payments → [+ Record Payment]
  → Select vendor, amount, mode (NEFT/UPI/Cheque/Cash), UTR ref
  → Confirm
  → System:
     • vendor closing_balance -= amount
     • vendor ledger row (PAYMENT, Dr)
     • Payment journal:
        Dr Vendor Payable
        Cr Bank/Cash
```

```
  → System checks:
```

## F.3 Financial Formulas

**GST Split:**
```
Intra-state:  CGST = Taxable × Rate/200 ; SGST = Taxable × Rate/200 ; IGST = 0
Inter-state:  IGST = Taxable × Rate/100 ; CGST = 0 ; SGST = 0
```

**Effective Price:**
```
P_eff = TierPrice × (1 − PkgDiscount/100) × (1 − ManualDiscount/100)
Taxable = Round(P_eff × Qty, 2)
```

**Round-Off:**
```
GrandTotal = Round(ExactTotal) to nearest rupee
RoundOff = GrandTotal − ExactTotal
```

**Double-Entry Invariant:**
```
Σ Debits = Σ Credits  (for every journal)
```

**Account Closing Balance:**
```
Closing = Opening + ΣDebits − ΣCredits  (debit-natural)
Closing = Opening + ΣCredits − ΣDebits  (credit-natural)
```

**DSO:**
```
DSO = (AR Closing / Credit Sales) × Days in Period
```
